# 한국어 문장 규칙

문장이 어색하면 읽는 사람은 내용보다 문장에서 먼저 멈춘다. 이 스킬은 그렇게 멈추게 만든 표현을 실제 사례에서 모은 체크리스트다. §1(번역투)은 외부 분류에서 가져왔고, 나머지 항목은 실제로 지적받은 것이다. 지적받은 적 없는 규칙은 넣지 않고, 쓸모가 없어진 규칙은 다음 사람이 지운다.

## 적용 범위

판단 기준은 매체보다 읽는 사람이다. 코드 옆에 있든 티켓 안에 있든, 남이 읽는 한국어 산문이면 대상이다.

- **채팅 답변과 코드 주석:** 아래 체크리스트의 §1~§3 항목, 「개발 용어는 그대로 쓴다」, 「마지막 점검」을 본다. §4 항목은 보지 않는다.
- **문서·티켓·공지처럼 남에게 넘기는 글:** 체크리스트 전체를 보고, 넘기기 전에 `reference.md` 를 읽는다. 각 항목의 근거, 바꿀 말, ❌/✅ 예시가 그 파일에 있다.
- **체크리스트 항목에 해당하는데 무엇으로 고칠지 모를 때:** `reference.md` 의 같은 절 번호를 찾아 읽는다.
- **쓰지 않는 경우:** 영어 문서, 사용자가 쓴 문장을 그대로 인용할 때.

## API 로 한글을 넣을 때

한글을 `\uXXXX` 로 바꿔서 넘기지 않는다. 예외는 없다. 한 자리만 틀려도 「몫이」가 「몷이」, 「굉장히」가 「굴장히」처럼 그럴듯한 다른 글자가 되고, JSON 도 API 도 에러를 내지 않는다. 노션·Confluence 같은 API 로 문서를 고칠 때 해당하고, 사례는 `reference.md` 맨 앞에 있다.

## 0. 넘기기 전에 훑는 목록

해당한다고 다 고치지는 않는다. 아래 「고치지 않는 것」을 같이 본다.

- [ ] 같은 동사가 세 번 넘게 나오나. 잡다·짚다·걸리다·갈리다·박다·가르다 (§3-1, §2-1)
- [ ] 영어 비유를 그대로 옮긴 명사가 있나. 천장·바닥·축·지문·덩어리·배선 (§2-1)
- [ ] 「A가 아니라 B」 대구가 두 번 넘나 (§3-2)
- [ ] 긴 문장을 끊었나, 끊은 뒤 앞 문장과 이어 읽히나 (§3-3)
- [ ] 볼드 소제목과 그 아래 첫 문장이 같은 말인가 (§3-4)
- [ ] 나란히 놓은 둘의 층위가 맞나 (§3-5)
- [ ] 「없는·않는」이 앞뒤 둘 다에 미치나 (§3-6)
- [ ] 대시(—)가 본문에 두 번 넘게 나오나 (§3-7)
- [ ] 문어체 사이에 「~고요·~거든요」가 섞였나 (§3-8)
- [ ] 볼드가 한 문단에 둘 넘게 붙었나, 이모지가 장식으로 붙었나 (§3-9)
- [ ] 할 말을 안 하고 예고만 한 줄이 있나 (§3-10)
- [ ] 번역투 구문이 있나. 「~를 필요로 하다」「~를 통해」「~에 의해」, 무생물 주어 「표가 보여준다」 (§1)
- [ ] 뜻이 비어 있는 표현이 있나. 비유 「선다」「닿는다」, 관용구 「조건이 됐다」「중요한 역할을 한다」「~할 때입니다」 (§2-1, §2-2)
- [ ] 「여기까지는」「이는」이 무엇을 가리키는지 하나로 정해지나 (§2-3)
- [ ] 「두 겹의」처럼 수만 말하고 각각이 무엇인지 안 밝혔나 (§2-4)
- [ ] 처음 꺼내는 사실을 「~인데」나 앞선 참조에 숨겼나. 대조로 쓴 「~인데」는 괜찮다 (§2-5)
- [ ] 문서가 자기 자신을 설명하는 문장이 있나 (§4-1)
- [ ] 읽는 사람이 멈출 용어가 있나. 개발자가 읽는 글이면 개발 용어는 그대로 둔다 (§4-2)
- [ ] 검토 과정이나 버린 안이 본문에 남았나 (§4-3)
- [ ] 확정 안 된 예시가 확정처럼 적혔나 (§4-4)
- [ ] 표에 「무엇을」만 있고 완료 기준이 없나 (§4-6)
- [ ] 그 지표가 다른 정책 때문에 저절로 움직이나 (§4-7)
- [ ] 수식어가 나중에 넓힐 것까지 막고 있나 (§4-8)
- [ ] 위 문서가 아래 문서를 담고 있나 (§4-9)
- [ ] 마지막으로, 처음 읽는 사람이 되어 끝까지 읽었을 때 멈추는 곳이 없나, 깨진 글자가 없나 (아래 「마지막 점검」)

## 개발 용어는 그대로 쓴다

채팅 답변, 코드 주석, MR·이슈 본문, 기술 문서처럼 개발자가 읽는 글에서는 캐시·렌더링·훅·쿼리·배포·머지·리베이스·API·스키마·브랜치 같은 용어를 우리말로 풀지 않는다. 코드 식별자, 명령어, 에러 메시지, API 필드명은 원문 그대로 쓰고 백틱으로 감싼다. 고칠 대상은 용어를 감싼 문장이다. 「캐시를 박아 둔다」에서는 「박다」를 고친다. 온보딩·리텐션·퍼널 같은 업계 유행어와 천장·축 같은 영어 비유는 개발자가 읽는 글이어도 바꾼다(§4-2).

## 고치지 않는 것

위 목록은 자주 나온 표현을 적은 것이고 금지어 목록과는 다르다. §2-1 의 빈도(잡다 357회 등)는 쓴 횟수이지 틀린 횟수가 아니다. 목록에 있다는 이유만으로 고치면 글이 더 나빠진다.

판정 방법은 바꿔 넣어 보는 것 하나다. 「징후」 「부분」 「정하다」로 바꿔서 뜻이 그대로면 원래 말이 비어 있던 것이고, 어색해지거나 뜻이 좁아지면 제자리에 쓴 것이다. 제자리에 쓴 말은 세 번을 넘겨도 그대로 둔다.

그대로 두는 것은 다음과 같다.

- 글쓴이가 왜 그 말을 골랐는지 설명할 수 있는 선택. 설명이 되면 버릇이 아니다.
- 문장 길이의 들쭉날쭉함. 고르게 다듬으면 그것이 AI 글의 리듬이다.
- 스스로 뒤집거나 덧붙이는 말. 「'거의'라고 쓰고 싶은데 실제로는 전부였다」
- 정리되지 않은 판단. 「맞는 것 같은데 걸리는 게 있다」를 매끈하게 고치면 정보가 준다.
- 수치·고유명사·직접 인용·남이 쓴 문장.
- 개발 용어·코드 식별자·명령어·에러 메시지.
- 물리적인 뜻으로 쓴 말. 「건물이 선다」 「손이 닿는다」

횟수 기준(§3-1의 세 번, §3-2·§3-7의 두 번)은 문서 전체에서 센다. 기준에 못 미쳐도 한 문단에 서로 다른 문제가 서넛 겹치면 그 문단을 고친다. 대시 하나나 「잡다」 한 번만으로는 고칠 이유가 되지 않는다.

## 고칠 때의 순서

1. §4부터 본다. 넣지 말아야 할 내용이 있으면 문장을 다듬어도 소용없다.
2. §3 구조를 고친다. 긴 문장을 끊고, 층위를 맞추고, 반복을 센다.
3. §1·§2 표현을 바꾼다. 가장 눈에 띄지만 가장 나중에 한다.
4. 소리 내어 한 번 읽는다. 숨이 차는 곳이 끊어야 할 곳이다.
5. 처음 읽는 사람이 되어 처음부터 끝까지 읽는다(아래 「마지막 점검」).

의미는 바꾸지 않는다. 표현을 덜어내다 주장까지 덜어냈으면 되돌린다.

## 마지막 점검

규칙을 다 지켜도 글 전체가 안 읽히는 경우가 있다. 항목별로 고치다 보면 문서를 이미 아는 사람의 눈으로 보게 되기 때문이다. 넘기기 전에 그 문서를 처음 보는 사람이 되어 위에서 아래로 한 번 읽는다. 멈추는 곳이 있으면 거기가 고칠 곳이고, 대개 다음 넷 중 하나다.

| 멈추는 이유 | 고칠 곳 |
|---|---|
| 처음 나온 말인데 설명이 없다 | §2-5 · §4-2 |
| 이 숫자가 어디서 나왔는지 모르겠다 | 근거를 그 자리에 한 줄 |
| 앞에서 한 말과 다르게 읽힌다 | 둘 중 하나를 고쳐 맞춘다 |
| 왜 이 이야기가 지금 나오나 | 순서를 바꾸거나 이어 주는 한 줄을 넣는다 |

깨진 글자도 본다. 특히 표 셀과 두세 글자짜리 구절을 본다. 긴 문장은 틀리면 앞뒤가 안 맞아 저절로 눈에 띄지만, 「몫이」 「안팎」처럼 짧은 것은 문맥이 없어서 틀린 채로 읽힌다.
