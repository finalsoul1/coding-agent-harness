# 상급자 보고 초안

보고는 매체가 아니라 관점이다. 읽는 사람이 알아야 할 것은 **내가 무엇을 관측했는지가 아니라, 무엇을 하기로 했고 그게 안전한지**다.
슬랙이든 이슈 코멘트든 문서든 구성은 같고, 길이만 다르다.

## 네 블록 (전부 필수)

내용이 없으면 블록을 지우지 말고 "해당 없음"이라고 쓴다. **특히 4번을 빼면 근거가 실제보다 강해 보인다.**

1. **결론** — 무엇을 어떻게 하는지 + 효과. 한두 줄. 조치가 아직 없으면 "무엇을 확인했고 다음에 무엇을 정해야 하는지".
2. **근거** — 표. 항목마다 확보량과 실사용을 나란히 둔다. 관측 구간과 조건을 표 위에 한 줄로.
3. **위험과 되돌리기** — "그러다 터지면?"에 대한 답. 무엇이 완충이고, 되돌리는 데 얼마나 걸리고, 언제 다시 볼지.
4. **확인하지 않은 것** — 측정 안 한 지표, 범위 밖으로 둔 대상, 추정으로 남은 부분.

## 제목은 조치, 관측값이 아니다

| 안 됨 | 됨 |
|---|---|
| 이벤트 구간 실측 - 24대가 0.8코어를 썼다 | 운영 API 서버 대수 축소 (24 -> 12) |
| API 응답 지연 조사 결과 | 주문 화면 지연 원인 확인, 캐시 적용으로 해소 |

관측값이 제목이 되면 읽는 사람이 "그래서 뭘 하겠다는 건데"를 스스로 조립해야 한다.

## 용어를 번역한다

| 원래 표현 | 보고 표현 |
|---|---|
| pod, 파드 | 서버 |
| minReplicas / maxReplicas | 기본 대수 / 증설 상한 |
| limit 대비 사용률 | 확보한 자원 중 실제 사용 |
| RSS, working set | 메모리 사용 |
| CPU throttling | 처리 지연 |
| canary, blueGreen, 롤아웃 | 새 버전 배포 |
| HPA 증설 | 자동 증설 |
| OOMKill, restart | 서버 재시작 |
| p95 / p99 | 느린 요청 기준 응답시간 |

파일명, 설정 키(`minReplicas` 등), 이슈 번호는 **번역하지 않고 그대로** 쓴다. 다만 결론과 근거 블록에는 넣지 않고, 링크나 상세 쪽에 둔다.

## 숫자는 단독으로 쓰지 않는다

절대값만 적으면 크고 작음을 판단할 수 없다. **확보량 대비**로 쓴다.

- 안 됨: "CPU 0.8코어를 썼습니다"
- 됨: "확보해둔 48코어 중 0.8코어(1.7%)를 썼습니다"

비용 절감액이나 반납 자원량은 결론에 넣되, 그 숫자가 어떤 전제에서 나온 값인지 한 줄로 밝힌다.

## 출력

**같은 내용을 길이 두 버전으로 낸다.** 보내는 자리가 정해지지 않은 경우가 많고, 둘 다 필요한 경우도 잦다.

- **짧은 버전** — 슬랙용. 표 없이 불릿 3~4개, 5~10줄. 블록 4개를 한 줄씩으로 압축한다.
- **긴 버전** — 이슈 코멘트·문서용. 표 포함, 블록 4개를 헤딩으로 분리.

HTML 문서로 남길 때는 `report-html` 스킬의 양식에 블록 4개를 섹션으로 넣는다.

짧은 버전이 실제로 슬랙에 나간다면 **`slack-draft` 스킬을 호출해 문체를 입힌다**(호칭·인사·요청 한 줄·금지 규칙). 이 스킬은 무엇을 담을지를 정하고, 문체는 그쪽이 정한다.

## 흔한 실패

| 실패 | 왜 생기나 | 교정 |
|---|---|---|
| 제목이 관측값 | 조사하던 관성이 그대로 남는다 | 조치와 효과로 바꾼다 |
| 기술 용어가 그대로 | 나에게는 그게 제일 정확한 단어다 | 번역표를 훑는다 |
| 위험·되돌리기 누락 | 내가 이미 안전하다고 판단해서 | 읽는 사람은 그 판단 과정을 못 봤다 |
| 확인 안 한 것 생략 | 짧게 만들려다 제일 먼저 잘린다 | 이게 빠지면 근거가 과대평가된다 |
| 근거 표에 파드 이름·해시 | 재현성을 챙기려다 | 그건 기술 기록용 코멘트에 따로 남긴다 |

## 예시 (긴 버전)

```markdown
## 운영 API 서버 대수 축소 (24 -> 12)

**결론** — 10/1 할인 이벤트 최대 유입에서도 API 서버가 확보해둔 자원의 2% 미만을 썼다.
대수를 절반으로 줄여 24코어 / 24GiB를 반납한다. 서비스 영향은 없다.

**근거** — 이벤트 전후 4시간(10/1 10:00~14:00) 운영 지표

| 항목 | 주문 API 서버 | 알림 발송 서버 |
|---|---|---|
| 서버 대수 | 24대 | 6대 |
| 확보한 CPU | 48코어 | 12코어 |
| 실제 사용 CPU | 약 0.8코어 (1.7%) | 약 0.1코어 (0.8%) |
| 메모리 사용 | 한도의 9.1% | 한도의 6.4% |
| 자동 증설 / 재시작 | 없음 / 0건 | 없음 / 0건 |

같은 구간에서 CPU가 가장 올라간 순간은 이벤트 유입이 아니라 새 버전 배포로 서버가 뜨는 비용이었다.

**위험과 되돌리기**
- 유입이 급증하면 자동 증설이 즉시 따라오지 못한다. 그래서 절반까지만 줄이고 증설 상한은 그대로 둔다.
- 이상 시 설정 한 줄 복구로 10분 내 되돌린다.
- 축소 후 2주간 지표를 보고 다음 단계를 판단한다.

**확인하지 않은 것**
- 유입 규모를 요청량 수치로 환산하지 않았다. 사용률 기준 판단이다.
- 알림 발송 서버는 이번 대상이 아니다. 대량 발송 대비 물량이라 별도 판단이 필요하다.
```
